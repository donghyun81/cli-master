# Server Data Ownership — 데이터 처리·스키마·삭제·왕복 규약 (앱 무관)

> **단일 목적**: 앱의 사용자 데이터를 서버가 소유할 때 **어떻게 나누고 · 스키마를 어떤 형태로 짜고 · 삭제를 어떻게 전파하고 · 왕복을 어떻게 묶고 · 무엇을 검증하는가**의 단일 규약. 도메인 무관 = **신규 앱이 propagation 으로 그대로 상속**한다.
> **상위**: `COMMON_ARCHITECTURE.md §4`(사용자 데이터 SoT = 서버 authoritative). 본 문서 = 그 §4 의 **형태 층 상세**이며, §4 가 정한 「무엇이 SoT 인가」 위에 「그럼 어떤 모양으로 두는가」를 얹는다.
> **결정 기록**: `ADR-0001-SERVER-DATA-OWNERSHIP-SEPARATION`(Coin 확정 2026-08-01). 본 문서 조항의 **변경은 새 ADR 로** 한다 — 이 file 을 직접 고쳐 덮지 않는다(§9). **추가 결정**: `ADR-0002-SERVER-WRITE-PATH-BEYOND-SYNC`(Accepted 2026-08-02 · §5-1 근거). ADR-0001 을 **대체하지 않고**(supersede 아님) 그것이 남긴 공백 1칸(= writer 수)을 채운다.
> ★**supersede 고지**: 본 문서 §3-2 는 구 `COMMON_ARCHITECTURE §4.1` 의 「중첩/구조화 객체 = JSONB · 중첩 필요 시 JSONB 승격」을 **대체**한다. §4.1 은 본 cycle 에서 함께 정정된다.
> **유래**: Selfward 「나에게로」 P1(서버 소유 재정의 · 2026-07-31~08-01) 실측. 각 조항의 `근거` = 그때 무엇이 틀렸었는지.
> **연관**: `MODEL_SEPARATION.md` · `SSOT_PRINCIPLES.md` · `docs/rules/supabase-handling.md`(운영 채널)

## 0. 이 문서를 읽어야 하는 때

- 서버에 **사용자 데이터 테이블을 새로 만들 때**
- 로컬(Room/DataStore) 에 있던 것을 **서버로 이관할 때**
- 기존 테이블에 **컬럼을 더하거나 뺄 때**
- 「기기가 바뀌어도 이어진다」를 **처음 설계할 때**
- ★**「이것들 비슷하니까 한 테이블로 묶을까?」 하는 순간** (= §2)

## 1. 소유 경계 — 무엇이 서버로 가는가

| 가는 것 | 안 가는 것 |
|---|---|
| **값을 치른 것**(과금·광고로 얻은 산출물) | **기기 파생물**(로컬 파일 경로 · 캐시 키 · 기기 id) |
| **자기저작**(사용자가 쓰고 만든 것) | **표시 계산물**(파생 가능한 집계·정렬 결과) |
| 그 둘의 **순서·구조**(정렬 순서 · 참조 관계) | **세션 상태**(현재 화면 · 스크롤 위치) |

★**판정 1문**: 「기기를 잃어버렸을 때 사용자가 **잃었다고 느끼는가**?」 그렇다면 서버로 간다.
★기기 경로(`localPath`)는 다른 기기에서 무의미하다 — 올리지 않고, 복원은 서버 경로로 **재다운로드**한다.

> **근거**: 「서버에 올려도 연동 없이는 꺼낼 수 없다」 — 익명 uid 가 기기 단독이면 서버 저장의 값이 0 이다. **연동(열쇠) + 서버 저장(데이터)은 선후가 아니라 한 덩어리**다.

## 2. ★확장을 전제로 나눈다 — 통합의 유혹과 그 값

### 2-1. 「지금 비슷하다」는 통합의 근거가 **아니다**

새 데이터 종류 3개가 필드가 겹칠 때 한 테이블 + `kind` 컬럼으로 묶고 싶어진다. 그 판단이 보는 것은 **오늘의 모양**이고, 보지 않는 것은 **내일의 축**이다.

**어떻게 변할지 모르는 것을 왜 미리 합치는가.** 합치는 것은 지금 1분을 아끼고, 나누는 것은 나중에 하루를 아낀다.

> **근거**: 산출물 3종(한마디·답장·이야기)을 `artifacts` 1 테이블 + `kind` 로 묶으려 했다. 그때 든 이유는 **「지금 필드가 사실상 같다」** 하나뿐이었다. 그런데 이야기는 **이미 축 8개**(장르·결말·역할·시선·비유 / 짜임·결·건네는 자리)를 갖고 있었다 — 합쳤다면 그 8개가 갈 자리가 없어 전부 `jsonb` 로 들어갔을 것이다.

### 2-2. 통합의 진짜 값 = **검사 능력을 잃는다**

통합의 비용은 「테이블이 커진다」가 아니다. **종별로 다른 제약을 걸 수 없게 되는 것**이다.

| 나누면 걸 수 있는 것 | 합치면 |
|---|---|
| 종류 A 에만 `UNIQUE(user_id, record_id)`(1:1 강제) | 못 건다 — 종류 B 는 1:N 이니까 |
| 종류 B 에만 `NOT NULL`(그 종류엔 필수) | 못 건다 — 종류 A 엔 없는 필드니까 |
| 종류별 열거형 `CHECK`(시에 소설 축 차단) | 못 건다 — 한 컬럼이 두 어휘를 받아야 하니까 |
| 종류별 인덱스(조회 패턴이 다르니까) | 반쪽만 — `kind` 를 앞에 붙인 복합 인덱스로 우회 |

★**못 거는 제약은 사라지지 않는다 — 앱 규약으로 내려간다.** 그리고 앱 규약은 **다음 사람이 모른다**. DB 가 거부해주던 것을 리뷰가 잡아야 하는 상태가 된다.

> **근거**: 실제 감사에서 나온 결함 중 「구조 검사 0 · 열거형 무검사 · 멱등 키 부재」는 **전부 버그가 아니라 「제약을 안 걸어서」 생긴 것**이었다. 같은 방식으로 테이블을 4개 더 만들면 결함이 4벌 는다.

### 2-3. 비용 계산법 — **분리는 덧셈, 통합은 곱셈**

- **분리 비용** = 테이블 1개 · RLS 4정책 · 매핑 1벌. 종류가 늘면 **선형으로** 는다.
- **통합 비용** = (못 건 제약 개수) × (그 제약이 지켜지는지 확인해야 하는 모든 자리). 종류가 늘면 **곱해진다.**

⟹ 종류가 **늘어날 것 같으면** 나눈다. 「늘어날지 모르겠다」도 늘어난다에 가깝다 — 줄어드는 경우는 드물다.

### 2-4. 그럼 언제 합쳐도 되는가 (예외 조건 2 · **둘 다** 충족)

1. **갈리는 축이 이미 밖으로 나가 있다** — 두 종류를 가르는 요소가 **자식 테이블로 분리돼 거기서 엄격히 검사**된다.
2. **부모 층에서 필드가 완전 동형이다** — 「거의 같다」가 아니라 **같다**.

> **적용 예**: 이야기와 시는 한 테이블(`compositions` + `form`)에 뒀다. 본문·출처·조각이 **완전 동형**이고, 갈리는 것은 **축 어휘뿐인데 그 축은 자식 테이블로 나갔다**. 그리고 자식에서 복합 FK `(composition_id, form)` 로 부모의 `form` 을 되짚어 **「시에 소설 축이 들어올 수 없다」를 DB 가 거부**한다. ⟹ **분리가 필요한 축은 분리했다.** 이건 예외가 아니라 원칙의 적용이다.

### 2-5. 참조도 같은 판단을 받는다

「오프라인이라 순서가 꼬일 수 있으니 FK 를 느슨하게」는 **확장성이 아니라 포기**다. 순서 문제는 **앱이 참조 대상을 먼저 올리면 되는 문제**이고, 대부분의 앱은 이미 그렇게 한다.

★**고아가 구조적으로 가능한 스키마를 고를 이유가 되지 않는다.** 순서를 지키는 것은 앱의 일이고, 어겼을 때 **거부당하는 것이 정상**이다. (단 §3-6 의 예외 1문은 별개다 — 그건 느슨함이 아니라 **계약**이다.)

### 2-6. 확장 지점을 **미리 비워두지 않는다**

「나중에 뭐가 올지 모르니 `meta jsonb` 하나 열어두자」 = **가장 흔한 자기기만**. 확장 지점은 **컬럼을 더하는 것**(additive ALTER)이지 자유 공간이 아니다. additive 는 싸다 — 값이 없으면 `null` 이고 구 클라는 안 보낸다.

> **근거**: 그렇게 열어둔 `records.meta jsonb` 는 **172/172 행이 `{}`** 였다. 서버·EF 는 지원하는데 클라가 한 번도 보내지 않았다 — 파이프는 뚫려 있고 물이 안 흘렀다. `jsonb` 는 「나중에 정할게」의 다른 이름이고, **나중은 오지 않는다**.

## 3. 스키마 형태 — 분리 + 엄격 6

### 3-1. 종별 테이블 (§2 의 결론을 스키마 문법으로)
한 테이블에 두 종류를 담지 않는다. 예외 = §2-4 의 조건 2 **둘 다** 충족.

### 3-2. 배열·구조체 = 자식 테이블 (신규 `jsonb` = 0) ★구 §4.1 대체
`sources[]` · `tags[]` · `axes[]` 는 **행**이 된다. `position integer` 로 순서를 지고, PK = `(parent_id, position)`.

| 형태 | 처분 |
|---|---|
| **단순 문자열 리스트**(태그·선호 등 · 구조 없음 · 종별 제약 불요) | `TEXT[]` **존속**(구 §4.1 계승) |
| **구조를 가진 항목의 목록**(필드 2개 이상 · 순서가 의미 있음) | ★**자식 테이블**(구 §4.1 의 「JSONB 승격」 **기각**) |
| **우리가 형태를 정하지 않는 외부 페이로드**(타사 응답 원문 등) | `JSONB` **허용**(우리 스키마가 아니므로 검사 대상도 아니다) |

★**갈림길 1문**: 「이 안의 필드에 **제약을 걸고 싶어질 것 같은가**?」 그렇다면 자식 테이블이다. `JSONB` 는 **제약을 걸 수 없다는 선언**이고, 그건 외부 페이로드에만 맞는 말이다.

### 3-3. 열거형 = CHECK — ★**단 값 SoT 가 repo 안에 있을 때만**
- 값 집합 = **(live distinct) ∪ (repo 선언값)**. 어느 한쪽만 보면 틀린다.
- ★**값을 정하는 주체가 repo 밖(외부 콘솔·타사 API·사람이 바꾸는 설정)이면 CHECK 를 걸지 않는다.** 구조 제약(`NOT NULL`·`length>0`)까지만.

> **근거 3**: ⑴ 카탈로그 축 — DDL 주석은 5종인데 live 는 8종(나중에 추가분). 주석대로 썼으면 **ALTER 자체가 실패**. ⑵ 결제 SKU — live 2종인데 코드 선언 4종. live 대로 썼으면 **아직 안 팔린 SKU 의 실구매가 거부**. ⑶ 광고 보상 항목 — 값 주인이 외부 콘솔이고 repo 안 검증이 0. 화이트리스트를 걸었으면 콘솔에서 이름 한 글자 바꾸는 순간 **서명 통과한 정상 콜백이 거부되어 적립이 조용히 깨진다**. 그건 검사가 아니라 **외부 설정에 대한 숨은 결합**이다.

### 3-4. 멱등 키는 **클라가 발급**한다
`UNIQUE (user_id, client_id)` — `client_id` = 로컬 PK 를 그대로 올린다. 서버 uuid 를 키로 쓰면 오프라인에서 만든 것을 식별할 수 없다.

### 3-5. `created_at` = **클라 생성 시각** (서버 `now()` 금지)
복원(hydration) 할 때 서버 시각을 쓰면 **원래 순서가 무너진다** — 전부 복원 시점으로 뭉친다.

### 3-6. FK 판정 기준 = **「참조가 대상보다 오래 살아야 하는가」**

| 답 | 처분 | 예 |
|---|---|---|
| **아니오** | **FK + `ON DELETE CASCADE`** (복합 FK 포함) | 기록에 붙은 AI 산출물 · 기록에 붙은 사진 참조 |
| **예** | **FK 없음 + 근거를 주석에 남긴다** | 「원본이 지워져도 목록 표시는 유지」가 계약인 **출처 스냅샷** |

★**엄격이 계약을 파괴하면 그건 엄격이 아니다.** 스냅샷에 CASCADE 를 걸면 기록 하나 지울 때 지난 산출물의 출처 줄이 조용히 사라진다.
★부모 키가 `(user_id, client_key)` 복합 UNIQUE 면 **복합 FK 가 성립**한다.

### 3-7. 자식 테이블 RLS = **부모 소유 EXISTS**
자식에 `user_id` 를 중복 저장하지 않는다:
```sql
USING (EXISTS (SELECT 1 FROM parent p WHERE p.id = child.parent_id AND p.user_id = (SELECT auth.uid())))
```
★`auth.uid()` 는 **`(SELECT auth.uid())` 형태**로 쓴다(행마다 재평가 회피).

## 4. 삭제 = **3층 계약** (하나라도 빠지면 「지운 것이 되살아난다」)

| 층 | 무엇 | 없으면 |
|---|---|---|
| **로컬 tombstone** | 지운 사실을 기록하는 작은 표 `{ id, 지운시각 }` | 오프라인에서 지우면 **말해줄 근거가 안 남는다**(행이 사라졌으니까) |
| **wire 전파** | 동기화 요청에 `deletedIds[]` 동봉 · 성공 시 tombstone 소거 | 서버 행이 영원히 살아 **복원 때 부활** |
| **DB CASCADE** | 부모 삭제 → 자식 자동 정리 | 자식이 고아로 남는다 |

### 4-1. 규약
- **한 요청 안에서 `upsert` 먼저 → `delete` 나중.** 반대면 편집-후-삭제가 뒤집힌다.
- **삭제는 멱등** — 없는 id 를 지워달라 해도 **성공**(0행). 재시도가 안전해야 발신 측이 재시도할 수 있다.
- **삭제 전용 EF 를 새로 만들지 않는다** — 멱등 키가 같고, 삭제는 늘 push 와 같은 순간이며, 한 요청 안에 있어야 **순서 역전이 구조적으로 불가능**해진다.
- **로컬 store 에는 삭제 API 가 반드시 있어야 한다.** `find`/`put` 만 있고 `remove` 가 없으면 **치우고 싶어도 치울 수단이 없다**.

> **근거**: 기록 삭제가 로컬 단독이었고(삭제 경로 전수에서 서버 호출 **0**), tombstone 인프라가 **전층 0 hit** 이었고, 복원은 `insertIgnoringExisting` 이라 서버 행을 전부 다시 넣었다. ⟹ **연동이 붙는 순간 「지운 기록이 재설치하면 되살아난다」.** 연동이 결함을 만든 게 아니라 **가려져 있던 걸 드러낸다**.

### 4-2. ★CASCADE 를 깔았다고 삭제가 되는 게 아니다
`ON DELETE CASCADE` 는 **부모 행이 서버에서 지워질 때만** 돈다. 그 삭제를 일으키는 채널이 없으면 **도미노는 세워져 있고 미는 손이 없다.** 스키마 cycle 에서 CASCADE 를 걸었다면 **전파 채널 cycle 을 반드시 뒤에 붙인다**.

## 5. 왕복 형태

- **테이블이 N 개여도 왕복은 1 쌍**(`sync-*` / `list-*`). 봉투 = 종별 배열. ★**분리는 스키마의 일이고, 왕복 수는 별개다** — 나눴다고 왕복이 늘어나면 그건 설계가 게으른 것이다.
- **자식은 부모 안에 중첩**(평면 배열 금지) — 부모 없는 자식이 **전송될 수 없게 shape 자체로** 막는다. DB 복합 FK 와 같은 취지를 wire 에서 반복한다.
- **자식 갱신 = 부모 1건 단위 delete-then-insert.** 자식은 `position` 이 순서를 지므로 부분 갱신이 의미 없다.
- **참조 순서** = 참조되는 축을 **먼저** 보낸다(기록 → 산출물). 복합 FK 가 그 순서를 강제한다.

### 5-1. ★**「왕복이 1 쌍이다」와 「writer 가 1 이다」는 다른 명제다**

`sync-*` 밖에서 서버가 직접 쓰는 경로(예: **생성 EF 가 산출물을 응답 만드는 김에 그 자리에서 INSERT**)가 생기면 — **왕복 수는 그대로인데 writer 는 2 가 된다.** 위 §5 는 전자만 말한다. 후자는 **금지되지 않으며**, 아래 3 을 **동시에** 충족할 때 성립한다(`ADR-0002-SERVER-WRITE-PATH-BEYOND-SYNC`).

1. ★**reader 를 함께 센다.** 그 행을 내려받는 경로가 **실재하는지**가 아니라, **그 경로의 게이트가 이 행에도 열려 있는지**를 센다. ★**배선이 있다 ≠ 배선이 돈다.**
2. **멱등 키 발급 주체는 그대로 클라다**(§3-4 불변). 서버가 써도 키는 클라 발급 `client_id` 를 그대로 쓴다 — 그래야 두 writer 의 같은 행이 `UNIQUE (user_id, client_id)` 위에서 겹친다.
3. **충돌은 DB 에 맡긴다.** UNIQUE + upsert 로 해소하고 **앱 로직으로 순서를 지키려 하지 않는다**(순서 보장은 프로세스 사망 앞에서 성립하지 않는다 — 애초에 그 사망을 막으려고 writer 를 늘린 것이다).

> **근거**: Selfward `SELFWARD-BG-1-SERVER-PERSIST-001`. 생성 EF 에 persist 를 붙이면서 「hydrate 가 이미 가져오므로 별도 배선 0」으로 판단했으나, 복원 usecase 의 게이트가 **uid 당 1회**(`HydrateOwnedUseCase.kt:75`)여서 **이미 복원을 마친 기기 = 실사용자 전원에게 아무것도 오지 않았다.** 역게이트 usecase(`RecoverGeneratedOutputsUseCase.kt:64`)를 신설해서야 닫혔다. **틀린 것은 결론이 아니라 census 의 축**이었다 — 「배선이 있는가」만 세고 **「게이트가 걸려 있는가」**를 세지 않았다.

> ★**환경 간 진실 차이 = 문면 위험**: 배포가 환경별로 갈리면 같은 문장이 한쪽에서 참, 한쪽에서 거짓이 된다. 사용자에게 하는 약속(「나가도 이어져요」)은 **prod 기준**이지 staging 기준이 아니다. 실측 = staging `story` v13 / `cumulative-insight` v10 ↔ **prod 둘 다 v5 무접촉**(2026-08-03).

## 6. 배포 순서 규율 (DDL ↔ 코드)

| 변경 | 순서 | 어기면 |
|---|---|---|
| **컬럼/테이블 추가** | **DDL 먼저 → 코드 나중** | 코드가 없는 컬럼을 쓴다 |
| **컬럼 제거** | ★**코드 배포 먼저 → `DROP` 나중** | **배포돼 있는 서버 코드가 즉시 깨진다** |
| **함수가 참조하는 컬럼 제거** | ★**함수 먼저 고치고 → 컬럼 제거** | 그 함수를 타는 경로 전체가 죽는다(예: 가입 trigger) |
| **이미 존재하는 테이블 변경** | ★**`CREATE TABLE IF NOT EXISTS` 금지 · `ALTER` 경로** | **조용히 no-op** 하고 migration 은 성공 보고 → 나중에 `42703` 으로 터진다 |

★**적용 전 「이 테이블이 이미 있는가」를 live 로 확인한다.** 설계 문서가 「신설」이라 적었다고 신설이 아니다.

## 7. 검증 규율 (「통과」가 무엇을 보장하는가)

1. ★**「발산 0」 앞에 「잰 게 있었는가」** — 비교 스크립트는 **행 수 하한 assert** 를 넣는다. 없으면 쿼리가 실패해 빈 파일 2개가 만들어져도 `diff` 가 「차이 없음」으로 통과시킨다. **빈 결과끼리의 일치는 일치가 아니다.**
2. ★**정의 변경 ≠ 동작 보증** — 함수 본문 sha 가 바뀐 것은 「그 경로가 돈다」의 증명이 아니다. **실제로 발화시켜** 결과를 확인하고 롤백한다.
3. ★**RLS 자동 활성 ≠ 정책 생성** — 정책 없는 RLS 는 전면 차단이고, 그건 500 이 아니라 **빈 결과**로 나타난다. 검증 = 「에러 없음」이 아니라 **테이블별 정책 수 census**.
4. ★**음성 대조 + 양성 대조 동반** — 「제약을 빼면 red 인가」와 「정상값이 실제로 통과하는가」를 같이 본다. 음성만 하면 **전부 거부하는 제약도 통과**한다.
5. ★**CASCADE 는 부모만 보면 검증되지 않는다** — 부모 삭제 후 **자식도 사라졌는지 같이 단언**한다.
6. **파괴적 처분은 데이터가 없을 때가 가장 싸다** — 출시 전 prod 행 0 이면 되돌리기 비용이 0 에 가깝다. 미루면 **실 원장 위에서** 해야 한다.
7. **역 migration 문장을 미리 적어 둔다**(실행 0). 되돌릴 일이 생겼을 때 그 자리에서 짓지 않는다.

## 9. 변경 정책

본 문서의 조항을 바꾸려면 **바꾸는 근거가 실측이어야 한다**(어느 앱에서 무엇이 어떻게 틀렸는지). 조항마다 붙은 `근거` 가 그 형식의 예다. 실측 없는 「더 나아 보인다」로는 바꾸지 않는다 — 여기 있는 조항 대부분이 **한 번 반대로 갔다가 되돌아온 것들**이다.

★특히 §2 는 **되돌아온 기록 그 자체**다. 통합·느슨 쪽을 한 번 권했다가 「어떻게 변할지 모르는데 왜 통합하나」로 기각됐고, 그 뒤 실측이 기각 쪽을 뒷받침했다. 다음에 또 통합이 매력적으로 보이면 **§2-2 의 표를 먼저 채워보라** — 못 걸게 되는 제약이 몇 개인지 세고 나서 판단한다.
